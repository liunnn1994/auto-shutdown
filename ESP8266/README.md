# ESP8266 无线广播认证固件

适用 **NodeMCU ESP8266 / ESP-12E**，固件版本 `radio-only-3`，协议版本 ASR2。
本仓库固件不适用于 ESP32。

上电即广播，PC 通过随机挑战和 HMAC 应答确认设备在线。无需连接路由器，
无需 Wi-Fi 账号密码或管理员账号，也没有网页、UDP/WebSocket 心跳和配网功能。
开发板插在普通市电上，PC 由 UPS 供电；PC 只扫描，不连接开发板热点。

## 烧录

1. Arduino IDE 安装 ESP8266 核心 3.x，按[根目录说明](../README.md)配置 `.env.local`。
2. 在仓库根目录执行 `./scripts/build-firmware.ps1 -PrepareOnly`，再用 Arduino IDE
   打开原始工程 `ESP8266/ESP8266.ino`。脚本在同目录生成 `radio_key.local.h`，
   该文件已被 Git 忽略。首次使用或修改密钥后，先重新执行生成命令再点击上传。
3. 工具 → 开发板选择 **NodeMCU 1.0 (ESP-12E Module)**，端口选择对应 COM。
4. Erase Flash 可选 `Only Sketch` 更新固件；如想清除旧版遗留的 Wi-Fi/管理员
   配置，可选 `All Flash Contents`。新固件不会读取或使用这些旧配置。
5. 上传后把开发板重新插在普通市电上；无需连接热点或配置任何网页。

命令行构建：

```powershell
./scripts/build-firmware.ps1
```

脚本每次从 `.env.local` 校验并注入密钥，缺失或无效时直接失败。生成的密钥头
位于 `ESP8266/radio_key.local.h`，不要提交或分享该文件。脚本优先使用 PATH 中的 `arduino-cli`，
也支持 Windows 默认安装位置的 Arduino IDE 内置 CLI。需要预先安装 ESP8266 核心。
检查构建成功后，按实际串口上传，
例如（将 `COM3` 替换为开发板端口）：

```powershell
arduino-cli upload -p COM3 --fqbn esp8266:esp8266:nodemcuv2 --input-dir target/esp8266-radio-only-3 ESP8266
```

保留该构建目录内的 `.elf` 和实际使用的核心版本，便于后续定位崩溃地址。
如果 CLI 不在 PATH 中，可使用 Arduino IDE 内置 CLI 的完整路径。
PC 和固件必须使用同一份构建密钥；修改密钥后需要重新构建两端并烧录。

## 广播行为

- AP 名称为 `auto-shutdown-六位芯片ID`，固定使用 2.4 GHz 信道 6。
- AP 使用每次启动随机生成且不公开的密码，防止客户端加入；关闭 DHCP。
  没有任何网络应用服务，认证信息通过管理帧广播传输，不需要 PC 加入网络。
- 只验证本协议的 HMAC 挑战，回复对应随机数、设备身份和诊断信息。
  不需要时钟同步；协议字段见 [根目录说明](../README.md)。
- 复位原因、异常原因/地址、内存和请求计数随每次认证应答传回 PC。
- 上电后尚未成功发布应答，或距离上次成功发布超过 45 秒时，LED 每 500 ms
  翻转一次；成功发布应答时点亮约 120 ms。重复随机数不会重新发布应答。
- 不读写 EEPROM，不保存运行时配置或日志。广播密钥从 `.env.local` 在构建时
  注入固件；AP 临时密码每次上电重新生成。
- 固定 8 槽请求队列与令牌桶限制验证负载，不覆盖待处理请求；缓存已拒绝的
  相同报文，记录最近 64 个成功应答随机数并在 10 分钟内拒绝重放。应答更新
  最短间隔 250 ms。具体限制及无法消除的无线干扰见根目录说明。

## 实机验收

1. 两端一起更新，退出旧 PC 程序。ASR2 不接受之前的 ASR1 应答。
2. 运行 `auto-shutdown.exe --radio-check`，检查 PC 主程序日志中的认证设备数。
   该入口只检查无线扫描与认证，不启动关机监控。退出码为 `0` 仍可能没有
   认证设备，必须确认日志中设备数大于 `0`，且出现预期 `radio://芯片ID`。
3. 启动正常 PC 软件，自动发现 `radio://芯片ID` 后开始监控；或手动输入标识，
   测试成功后点击“保存并启动监控”。单独测试不会切换监控目标。
4. `%USERPROFILE%/.auto-shutdown/logs/esp-日期.log` 应持续出现新的认证遥测，
   主程序显示在线。诊断入口本身不会写入该遥测文件。对当前目标成功认证前
   不会触发关机；成功在线后首轮认证失败变黄，恢复应答应重新变绿。
5. 保存工作后可拔掉开发板电源验证失联；约 180 秒后会弹出 60 秒倒计时，
   失联阈值从最后一次有效认证计算，在下一轮失败检查时判定，所以时间不保证
   恰好为 180 秒。倒计时归零会真实关机，可及时取消或重新上电验证自动恢复。
6. 验证取消本次关机后，持续失联不会重复提醒；设备恢复认证再失联才会重新
   提醒。验证“稍后关机”会在 30 秒后重弹完整 60 秒倒计时，期间恢复则取消重弹。

验收时记录两端版本、开发板芯片 ID、网卡与驱动、拔电/恢复时间及两类 PC 日志。
构建通过或 Rust 协议测试通过不能替代上述实机步骤。

若无法认证，检查 PC 无线网卡和定位权限，以及串口（115200）的
`radio AP`、`callback`、`radio stats`（rx/replies/bad/len）。本机 API 扫描成功
不能证明自定义 IE 在空中传递成功，SDK 与驱动的完整配合仍需烧录实测。
串口启动日志包含固件版本、构建时间、复位原因与目标标识；统计每 5 分钟输出
一次。`rx` 是 SDK 回调收到的匹配厂商请求数，`bad` 为长度或认证失败数，
`replies` 是应答序号（发布尝试数），不能单独用来证明 PC 已成功收到应答；
`dropped` 记录限流、去重、队列已满或发布间隔限制导致的丢弃次数。

请保留烧录版本对应的 `.elf`，以便用认证日志中的崩溃地址定位问题。
